# F1 2026 — 3D Career Racing Game — Build Plan

Goal: an offline, double-click `index.html` Formula 1 game (Three.js r158 UMD, classic
scripts, procedural assets) with the full 2026 grid, 24 circuits, a complete race
weekend, AI, career mode and broadcast-style UI. Budget: **< 128 MB total, target < 40 MB**.

This plan exists so the build can be delivered in **bounded sections** without exhausting
the agent context window. Each section has a hard scope, an exit test, and a git commit.
Every commit is runnable (no broken intermediate states).

---

## 0. Why sections?

A single-pass build of this spec is ~25–35k lines and would blow a context window several
times over. Instead each section is written, tested, committed, and then **forgotten** —
later sections only rely on the documented interfaces below, never on re-reading old code.
`BUILD_LOG.md` is the single source of truth for interfaces, test status and known gaps.

### Context rules used
- One section per turn-group; never open files from earlier sections unless debugging.
- A compact `BUILD_LOG.md` "interface card" is updated at the end of each section.
- Repetitive data (24 circuits) is **generated by script** from short definition files,
  not typed by hand, so it costs almost no context per circuit.
- Verification is automated (Node smoke test + headless Chromium screenshot), so bugs
  are found by tools rather than by re-reading code.

## Architecture (interfaces fixed in Section 1)

- Namespace: everything hangs off `window.F1`. No ES modules, no `fetch`, no CDN.
- Load order is explicit in `index.html`; later files may assume earlier globals.
- **Units:** metres, seconds, kilograms; +X east, +Z south, +Y up; yaw 0 = +Z? (fixed in S3 doc).
- **Rendering:** one `THREE.WebGLRenderer`, pixel-ratio capped, quality presets
  Low/Medium/High/Ultra. Static geometry merged/instanced; target < 400 draw calls.
- **Simulation:** fixed 120 Hz physics step + render interpolation; seeded RNG
  (`F1.rng(seed)`) drives AI/weather so races replay identically.
- **Data:** `F1.DATA.teams`, `.drivers`, `.sponsors`, `.circuits` (metadata),
  `.getCircuit(id)` → geometry + generated track model.
- **Saving:** `F1.storage` wraps `localStorage` in try/catch, JSON export/import fallback.
- **UI:** DOM overlay (`#ui`) over a full-window canvas; screens are functions returning
  nodes, HUD is a persistent layer. CSS only in `css/ui.css` (+ `css/hud.css` in S3).

## Circuit data strategy (Section 2)

Hand-tracing 24 real layouts is the largest data task. Compact per-track **corner/straight
segments** (distance in m, radius, angle, elevation) are expanded by a generator that:

1. builds a smooth Catmull-Rom centreline at 3 m spacing,
2. applies a least-squares closure correction so start/finish is exact,
3. rescales distances so lap length matches the real value to ±1 %,
4. derives width, kerbs, run-off, sector splits, 3 Boost zones, start line, pit lane.

Circuits are tagged `ACCURATE` (well-known geometry, close to real corner shapes) or
`APPROXIMATE` (new/changed tracks) in the data and in `README.txt`. Elevation profiles use
published key points (Eau Rouge, Casino square, COTA hill, etc.).

## Risk / fallback register

| Risk | Mitigation |
|---|---|
| 24 hand-built worlds too large | One theme-driven environment builder; per-circuit palette + feature flags |
| Context exhaustion mid-feature | Hard section boundaries; BUILD_LOG interface cards; script-generated data |
| file:// restrictions | Classic scripts only; data as `window.*` assignments; canvas textures |
| Low-end GPU | instancing, merged static meshes, auto-quality fallback, shadow budget |
| localStorage flaky on file:// | try/catch wrapper + export/import JSON + 3 slots |
| Career scope | Pure-JS simulation modules, DOM screens kept separate from 3D |

## Verification per section

1. `node tools/smoke.js` — loads every script in a fake-DOM sandbox, checks globals,
   syntax and data invariants (22 drivers, 11 teams, 24 rounds, 25 points table…).
2. `node tools/screenshot.js` — headless Chromium via puppeteer-core + `@sparticuz/chromium`,
   loads `file://.../index.html`, captures console errors and a PNG.
3. Manual preview server (`python3 -m http.server`) only as a convenience; the shipping
   target is `file://`.

## Feature cuts policy

Nothing in the spec is dropped without asking. If a cut becomes necessary it will be
proposed with the measured size/perf reason. Known simplifications already sanctioned by
the spec: approximated circuit geometry (tagged), stylised sponsor wordmarks (no logos),
simplified bicycle+Pacejka vehicle model (no heavy physics engine), procedural audio.
